### Current Execution And Recovery Shape

The eval runner validates its config and task/model references before preparing
the output directory. It then writes child attempt directories progressively.
Each attempt writes several payloads followed by its manifest. A policy-run
manifest is written only after all declared task attempts finish, and the
eval-suite manifest is written only after all policy runs and configured
replays finish.

Consequences after interruption:

```text
complete root manifest
  -> declared run/suite can be validated as a terminal artifact

missing root manifest with child directories
  -> current code has no authority for deciding which children belong to the
     intended run or are safe to reuse

non-empty output directory
  -> current command rejects it, unless --overwrite destroys and reruns it
```

The terminal attempt manifest is useful evidence but is not by itself a resume
declaration: it does not bind the orphan to the intended eval config hash,
selected task hash set, harness runtime, selected policy identity, or parent
eval-attempt id. This is why resume semantics cannot be inferred merely from
file existence.

### Artifact Economy Conclusion

The inventory does not justify a new global provenance manifest or a duplicate
artifact validator. Existing typed records already own task identity, training
lineage, adapter identity, runtime identity, attempts, and comparison inputs.

The genuine implementation gaps are:

1. one CPU-only consumer that names the canonical inputs, invokes the existing
   loaders and validators, reconstructs both decisions, regenerates reports in
   a disposable directory, runs the existing deterministic smoke, and records
   required pass/fail/skip results;
2. a repository command or internal composition boundary that builds policy
   selection from an eval suite instead of relying on an ad hoc analysis;
3. explicit resume/retry authority and tests after the semantic reuse unit is
   decided;
4. failure-injection coverage at the interrupted-suite level;
5. updated reproducibility documentation, because the existing document still
   describes filtering and training as future work;
6. an honest report of the historical absolute-path portability limitation.

A machine-readable reproduction plan is justified only if it uniquely freezes
the ordered canonical inputs, expected decisions, required checks, and optional
skips consumed by the new command. A wrapper script should remain a thin
entrypoint. A persisted resume record remains unjustified until the resume
authority cannot be derived safely from existing declarations and terminal
artifacts.

The answer must be pressure-tested against parent declaration identity,

## 2026-08-18 Checkpoint 4: Resume Unit And Retry Semantics

### Decisions

- Resume may reuse a successful completed agent-generation result, then reruns
  the remaining scorer and orchestration work. It does not reuse individual
  patch, public-check, or hidden-validator phases.
- Agent-generation completion requires an immutable terminal generation
  manifest. The producer writes the generation-owned payloads, validates them,
  and publishes that manifest last, before scoring starts. The final attempt
  manifest remains a separate terminal record written after scoring and must
  not be an updated form of the generation manifest.
- Files without the generation manifest are interrupted partial state, not a
  reusable checkpoint. When the final attempt manifest is absent, a valid
  successful generation manifest permits resume from the candidate patch; a
  valid terminal-failure generation manifest permits only preservation of that
  failure and completion of the outer orchestration record.
- A typed model timeout or model error is a terminal policy outcome. Resume
  preserves it and does not call the policy again. Additional policy samples
  belong to config-declared attempts or a new run, not to resume.
- A process interruption before a terminal generation result is different: no
  policy outcome was committed, so resume may rerun that incomplete declared
  attempt.

### Why This Boundary Matters

Retrying a policy after a recorded model failure would change the sampling
protocol and could improve the measured result merely by drawing again. That
would conflate infrastructure recovery with repeated policy attempts and make
the configured attempt count false. Provenance alone is insufficient: the
terminal manifest is the completion authority, and matching declaration
identity is still required before it can authorize reuse.

The separate generation manifest passes the artifact-economy gate. It uniquely
owns the fact that an expensive generation phase committed either a
scorer-consumable candidate or a terminal policy failure before the final
attempt existed. The resume consumer needs that fact, and it cannot be derived
from an absent final attempt manifest.

### Reuse Identity Decision

Reuse fails closed unless every semantic input represented by the interrupted
run declaration still matches. At minimum, the existing authorities are:

- the selected task's record inside `EvalTaskHashes`, which covers the task
  manifest and required task files;
- the eval-config content hash and the planned eval attempt, identified by its
  selected policy, task id, and attempt index;
- the selected policy's resolved-input provenance, including model config,
  model-input protocol, observed provider/model digest, decoding config, and
  any max-turns override for a model policy;
- `HarnessRuntimeProvenance`, whose derived hash covers `src/agentenv`,
  `pyproject.toml`, `uv.lock`, the Python implementation/version, platform, and
  machine architecture.

The resume consumer should compare these authoritative records rather than
trusting paths or a loosely defined compatibility claim. Config equality alone
is insufficient because the referenced model, decoding, protocol, or control
inputs can change without changing the eval-config file. Timestamps, durations,
and output locations are observations rather than semantic generation inputs
and should not create false incompatibility.

Under the strict Week 11 definition, any semantic drift rejects resume with a
typed reason. Intentionally evaluating an old candidate under changed harness
or scorer code is a new run or rescore experiment, not continuation of the same
declared run.

### Planned Eval Attempts Decision

The complete set of planned eval attempts is frozen before any attempt starts.
Each planned attempt is identified by the existing policy, task id, and attempt
index fields and receives its `eval_attempt_id` in that initial declaration.
This is a planned eval attempt, not a new "slot" or "attempt coordinate"
concept.

The declaration is immutable, so the planned attempt count cannot change in
response to observed policy outcomes. A generation checkpoint must reference
one declared `eval_attempt_id`, and the terminal result must contain exactly one
outcome for every declared attempt, with no undeclared or duplicate attempts.
Without this pre-execution authority, a child checkpoint could claim parent
membership and an interrupted run could silently omit planned work.

For an all-policies evaluation, the eval suite owns one immutable declaration
covering every policy, task id, attempt index, and preassigned
`eval_attempt_id`. It publishes that declaration before the first policy runs.
Policy runs consume their declared subsets; they do not create duplicate
declarations. The final suite result must match the declaration exactly.

### Corrupt Attempt Scope Decision

If a terminal generation manifest exists but is corrupt or fails validation,
only that planned eval attempt is rejected as evidence. Resume must not call the
policy again for that attempt, because a committed policy outcome may have been
lost or altered and another call would draw a replacement sample.

The runner continues independent planned attempts and preserves their valid
evidence. The final suite result identifies the rejected attempt and cannot
claim that the complete declared comparison is valid; policy selection or a
reproduction PASS must therefore fail or abstain. This is a suite-level validity
consequence, not a reason to discard valid sibling attempts or stop their
execution.

## 2026-08-18 Reproduction Claim Clarification

The existing `scripts/reproduce_core_smoke.sh` is a deterministic harness
integration smoke, not a reproduction of the Week 10 model comparison. It
validates the task pack and split lock, executes 18 control-policy eval attempts
across three tasks and six policies, runs the six configured policy-run
replays, and verifies that a report regenerated from that fresh suite is
byte-identical to the report emitted during the same invocation.

That proves the current locked environment can execute the task, agent-control,
scorer, replay, artifact, and report path coherently. It does not validate the
stored Week 10 SFT/DPO artifact graph, reconstruct the Week 10 abstention
decisions, compare against a checked-in canonical smoke result, rerun real-model
inference, or rerun training.

The Week 11 default must report the two claims separately:

- stored-evidence verification reconstructs the designated Week 10 evidence,
  decisions, and canonical reports from stored artifacts;
- deterministic harness smoke establishes that a small current executable path
  still works, without claiming to reproduce the Week 10 model result.

### Existing Control-Calibration Overlap

`agentenv controls run` already executes the scorer controls and scripted-agent
controls, persists their attempt artifacts, compares actual outcomes with
declared expectations, repeats them for normalized artifact-drift detection,
calibrates declared public-check idempotency, writes a typed control manifest
and report, and exits nonzero when the control run is not valid and stable.

The core smoke duplicates the scorer and scripted-agent execution. Its distinct
coverage is the eval-suite orchestrator, configured replay runner, eval-suite
artifacts, and generic eval-report reconstruction. However, its shell success
condition currently checks command completion and equality between two reports
generated from the same fresh suite. The eval report displays control
expectations and replay results, but the smoke does not explicitly fail merely
because a control is off-track or a replay result is a mismatch; two identical
reports can faithfully describe the same bad run.

Week 11 therefore must not add another deterministic control smoke. The
smallest useful Level 2 change is to reuse the existing core smoke surface and
make its distinct suite/replay/report assertions executable. Existing control
calibration remains the owner of repeated flake and public-check-idempotency
measurement.

## 2026-08-18 Checkpoint 5: Stored Policy-Selection Consumer

Added one read-only composition boundary that accepts an eval-suite directory
and returns the existing `PolicySelectionAnalysis`. It does not add a schema,
manifest, persisted artifact, CLI, report section, or alternate source of
selection authority.

Before reconstructing the decision, the consumer now:

- verifies the current eval-config bytes against the config hash frozen in the
  suite manifest;
- validates the config's referenced inputs and training/eval disjointness;
- checks that the suite declaration matches the config's task set, task hash
  set, policy order, policy inputs, attempt count, and replay count;
- reuses the trajectory builder to walk every child attempt, typed payload,
  live task hash, leakage check, and reward-hack check;
- requires the exact declared policy/task matrix and maps only validated
  attempt evidence into comparison cells.

The low-level cell mapper was narrowed to accept the status and prompt-loop
values it actually consumes. This keeps the suite consumer dependent on the
validated trajectory boundary instead of reloading a second, partly
overlapping attempt-summary representation.

Focused failure coverage proves that changed config bytes and missing attempt
evidence fail closed. A disposable two-policy suite reconstructs an abstained
complete tie from two typed policy failures.

The two stored Week 10 suites also reconstructed successfully:

```text
positive SFT comparison -> 24 cells, abstained, complete_tie, none
exploratory DPO comparison -> 18 cells, abstained, complete_tie, none
```

This checkpoint deliberately leaves the generic report renderer unchanged.
The designated Week 10 reports already regenerate byte-for-byte; adding a new
section would change the canonical bytes. The Level 1 verifier should therefore
check the reconstructed policy decision and canonical report bytes as separate
derived assertions over the same stored suite.

## 2026-08-18 Checkpoint 6: Level 1 Stored-Evidence Verifier

Added the CPU-only Level 1 composition. It validates the task pack and split
lock, reconstructs all three designated training graphs, reconstructs both
policy-selection decisions through the trajectory boundary, checks the pinned
outer suite and report hashes, and regenerates both reports into a fresh output
directory for byte comparison.

The exact canonical set now lives in
`configs/reproduction/posttraining_result.yaml`. This plan passed the artifact
economy gate:

1. It uniquely owns which otherwise internally valid training runs, eval
   suites, reports, and expected decisions are the designated result.
2. A repository maintainer writes it; the stored-evidence verifier consumes
   it.
3. Existing manifests can prove internal consistency and lineage, but cannot
   identify themselves as the canonical experiment among multiple valid runs.
4. Without the plan, a substituted but internally coherent result could pass
   validation without reproducing the designated result.

The plan intentionally does not copy internal task hashes, adapter hashes,
source membership, attempt identities, or runtime provenance. Their existing
manifests and loaders remain authoritative. It pins only each top-level
training/suite manifest, each canonical report, and the expected selection
decision.

The verifier returns one deterministic in-memory result containing 11 required
checks. Evidence failures are captured per check so independent artifacts can
still be inspected, while the overall result is `FAIL` if any required check
fails. Invalid plan syntax or an unsafe/non-empty output location still fails
before verification starts.

Canonical probe:

```text
task pack structure and splits                         PASS
three training artifact graphs                        PASS
SFT comparison: 24 cells, abstained, complete_tie     PASS
DPO comparison: 18 cells, abstained, complete_tie     PASS
two canonical report hashes                           PASS
two regenerated report byte comparisons               PASS
overall                                                PASS (11/11)
```

Focused tests include the real designated result and a synthetic report
renderer drift. The drift leaves the canonical report hash valid but makes the
regenerated-report check and overall result fail, proving that semantic
stored-evidence validation cannot mask changed report bytes.

## 2026-08-18 Checkpoint 7: Level 1 Command And Exit Semantics

Added the thin command:

```text
uv run --frozen agentenv reproduce stored-evidence --out <fresh-directory>
```

The command delegates every check to the Level 1 verifier, writes
`stored_evidence_verification.md`, prints the required-check count, and exits
`1` when any required check fails. Invalid plans and unsafe or non-empty output
directories fail before verification begins. The command adds no alternate
validation or decision logic.

Two real invocations against the canonical plan each returned:

```text
PASS stored-evidence checks=11/11
```

Their two regenerated reports and verification summaries were byte-identical.
A real invocation with one deliberately wrong canonical report hash returned
`FAIL`, reported `10/11`, wrote the failure summary, and exited `1`. Focused CLI
tests independently cover both status-to-exit mappings.
